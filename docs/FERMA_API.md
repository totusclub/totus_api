# Онлайн-касса Ferma (OFD.ru) — тестовые эндпоинты totus_API

Код: `lib/ferma/` (настройки, клиент, сборка чека, хранилище, сервис), `controllers/ferma.controller.js`, `routes/ferma.routes.js`.
План интеграции — `docs/claude/FERMA_INTEGRATION_RU.md`, тестирование — `docs/claude/FERMA_TESTING_RU.md`.

**Что есть сейчас:** отправка и проверка чеков в тестовом режиме, хранение чеков, повторы, возвраты, коррекции, callback, фоновая сверка, сверка с реестром Ferma, проверка кассы и самопроверка всего процесса.
**Временно для проверки:** `FERMA_RECEIPT_TRIGGER=booking` — чек на стенд при создании бронирования (раздел 7).
**Чего нет:** чеки при реальной оплате ВТБ (`utils/vtbCallback.js`, `/check_pay`) не пробиваются — это подключим отдельным PR, когда будут готовы оплата, данные поставщиков (ИНН / наименование / телефон туроператора) и ответы бухгалтера.

---

## 1. Режимы

| `FERMA_MODE` | Что происходит |
|---|---|
| `off` (по умолчанию) | Касса выключена. Эндпоинты отвечают 503, фоновой сверки нет. Поведение API без изменений |
| `test` | Запросы — только на `ferma-test.ofd.ru` (другой хост режим не пустит). Почта покупателя всегда `FERMA_TEST_EMAIL` — стенд общий. Самопроверка доступна |
| `live` | Боевая касса `ferma.ofd.ru`. Тестовые чеки **запрещены**; `FERMA_ALLOW_LIVE_RECEIPTS=1` открывает их только для одной проверки: сумма не больше 1 ₽, своя почта и поставщик обязательны. Самопроверка недоступна |

Переменные — раздел Ferma в `.env.example`.

## 2. Как включить тестовый режим на сервере

```bash
# .env (значения не коммитить)
FERMA_MODE=test
FERMA_LOGIN=…          # логин стенда для кассы ФФД 1.2 — документация Ferma §5.2
FERMA_PASSWORD=…       # пароль стенда — там же
FERMA_INN=3245001416   # тестовая организация стенда
FERMA_CALLBACK_SECRET=$(openssl rand -hex 16)   # необязательно: без него callback не передаётся

git pull && npm run check && pm2 restart api
pm2 logs api --lines 50 --nostream | grep FERMA   # [FERMA] mode=test host=ferma-test.ofd.ru inn=3245001416 worker=60s
npm run ferma:selftest                            # 15 шагов на стенде, в базу не пишет (--db — писать)
```

Таблица `fiscal_receipts` создаётся сама при первом обращении.

## 3. Эндпоинты

Все `/api/admin/fiscal/*` — только сотрудник (`Authorization: Bearer <staff JWT>`), всегда, независимо от `AUTH_MODE`.
Суммы во входных данных — рубли (`1500`, `"1500.50"`, `"1 500,50"`); в базе — копейки.

| Метод и путь | Что делает |
|---|---|
| `GET /config` | Режим, хост, ИНН, система налогообложения, тип агента, НДС, проблемы настроек, срок токена. Без пароля и секрета |
| `POST /token` | Получить новый токен Ferma — проверка логина и пароля |
| `GET /cashboxes` | Кассы: готовность, ФФД 1.2, признак агента, «только интернет», ИНН, место расчётов, тариф и ФН; `problems` и `warnings` |
| `GET /queue` | Длина очереди чеков у Ferma |
| `GET /ferma-status?receiptId=…` или `?invoiceId=…` | Статус любого чека прямо у Ferma (например, пробитого из Postman) |
| `POST /preview` | Собрать чек без отправки: тело запроса (почта скрыта), ошибки и предупреждения |
| `POST /receipts` | Создать и отправить тестовый чек (см. ниже) |
| `GET /receipts?state=&scenario=&orderRef=&limit=&offset=` | Наши чеки, новые сверху |
| `GET /receipts/:id?refresh=1` | Карточка чека и его возвраты; `refresh=1` — спросить статус у Ferma |
| `POST /receipts/:id/refresh` | Спросить статус у Ferma |
| `POST /receipts/:id/retry` | Новая попытка после `kkt_error` / `rejected` / `send_failed` — новый InvoiceId; можно поправить `amount`, `label`, `supplier`, `paymentMethod` |
| `POST /receipts/:id/refund` | Чек возврата к подтверждённому приходу: `{ "amount": 500 }`, без суммы — весь остаток |
| `POST /reconcile` | Фоновая сверка прямо сейчас |
| `GET /registry?date=ГГГГ-ММ-ДД` | Сверка наших чеков с реестром Ferma (list2). В test — только свои чеки, по одному: реестр общего стенда за день огромный |
| `POST /selftest` | Самопроверка на стенде (только test), отчёт по 15 шагам |

Публично: `POST /api/ferma/callback/:secret` — callback Ferma. Неверный секрет → 404. Тело callback не меняет статус: сервер отвечает 200 и сам спрашивает статус у Ferma (подписи у callback нет).

### POST /api/admin/fiscal/receipts

```json
{
  "scenario": "tour",
  "amount": 1500,
  "label": "Тур: Турция, 20.11-27.11.2026, заказ 123",
  "orderRef": "demo1",
  "supplier": { "inn": "7718221538", "name": "ООО Тестовый туроператор", "phone": "+74950000000" },
  "waitMs": 15000
}
```

| Поле | |
|---|---|
| `scenario` | `tour` — агентский чек, поставщик — туроператор; `arlekino` — агентский, поставщик — продавец размещения; `own_service` — собственная услуга без агентских полей; `correction` — чек коррекции прихода |
| `amount` | Рубли, больше 0, не больше двух знаков после запятой |
| `label` | Название позиции; длинное тире и «ёлочки» заменяются (касса их портит), больше 128 символов — обрезается с предупреждением |
| `orderRef` | Метка заказа `[A-Za-z0-9_.]`, по умолчанию — случайная. Повтор с той же меткой возвращает тот же чек (200, `reused: true`) |
| `supplier` | В test по умолчанию — тестовый поставщик; в live обязателен |
| `correction` | Для `correction`: `{ "description": "…", "receiptDate": "ДД.ММ.ГГ", "type": "SELF" }`; по умолчанию — вчерашняя дата |
| `paymentMethod` | Признак способа расчёта, по умолчанию 1 (предоплата 100 %) |
| `email` | Только в live (в test всегда тестовая почта) |
| `waitMs` | Сколько ждать финального статуса, по умолчанию 15000, максимум 60000 |

Ответ `201`: `{ ok, reused, warnings, receipt }`, где `receipt.state` — состояние (ниже), `receipt.ofdReceiptUrl` — ссылка на чек, `receipt.fiscal` — РНМ, ФН, ФД, ФП.
Ошибки: `400 invalid_receipt` + `errors` (например `invalid_supplier_inn`), `400 invalid_amount`, `403 live_receipts_disabled`, `503 ferma_not_configured` + `problems`, `502 ferma_error` + ответ Ferma.

### Состояния чека

| `state` | Значит | Что дальше |
|---|---|---|
| `draft` | Записан, ещё не отправлен | Отправится сразу |
| `sent` | Ferma приняла (StatusCode 0 / 1) | Фоновая сверка спрашивает статус: через 3 с, 30 с, 2 мин, 10 мин |
| `confirmed` | StatusCode 2 — чек в ОФД | Финал |
| `kkt_error` | StatusCode 3 — касса отказала, причина в `error.text` | Исправить и `retry` (новый InvoiceId) |
| `rejected` | Ferma отклонила запрос (ошибка данных) | Исправить и `retry` |
| `send_failed` | Сеть, тайм-аут, 5xx, «нет свободных касс», касса не готова | Сверка отправит **тот же** InvoiceId через 15 с, 1, 5, 15, 30, 60 мин — второй чек не создастся (Ferma ответит 1019, берём существующий) |

InvoiceId: `<префикс>-<orderRef>-<pay|ret|cor>-<попытка>`, например `tc-test-demo1-pay-1`.

## 4. Самопроверка (`POST /selftest`, `npm run ferma:selftest`)

1. Токен. 2. Касса: готова, ФФД 1.2, агент, интернет. 3. Очередь. 4. Тур: агентский приход → CONFIRMED. 5. Повтор того же чека — тот же чек, Ferma отвечает 1019. 6. Статус по InvoiceId = по ReceiptId. 7. Собственная услуга → CONFIRMED. 8. Частичный возврат → CONFIRMED, больше остатка — отказ. 9. Коррекция → CONFIRMED. 10. Неверный ИНН поставщика: наша проверка не пускает, Ferma отвечает 1085. 11. Сумма позиции не сходится → KKT_ERROR. 12. Испорченный токен — клиент сам берёт новый. 13. Поддельный callback не меняет статус. 14. Фоновая сверка: незавершённых нет. 15. Чеки есть в реестре Ferma.

## 5. Примеры

```bash
T="Authorization: Bearer $STAFF_JWT"; A=https://api.totus.club/api/admin/fiscal
curl -s -H "$T" $A/config
curl -s -H "$T" $A/cashboxes
curl -s -H "$T" -H 'Content-Type: application/json' -d '{"scenario":"tour","amount":1500}' $A/receipts
curl -s -H "$T" -H 'Content-Type: application/json' -d '{"amount":500}' $A/receipts/1/refund
curl -s -H "$T" -X POST $A/selftest
```

## 7. Чек при создании бронирования (временно, только test)

Чтобы посмотреть настоящие чеки по живым заказам, не дожидаясь подключения оплаты:

```bash
# .env — вдобавок к FERMA_MODE=test и доступам стенда
FERMA_RECEIPT_TRIGGER=booking
pm2 restart api
```

- Срабатывает в `POST /create-package` после записи заказа: тур Level.Travel (`scenario=booking_lt`) и номер Arlekino (`booking_arlekino`). Бронирование кассу не ждёт: чек уходит в фоне, ошибки — только в лог.
- **Только `FERMA_MODE=test`.** В `live` чек при бронировании не пробивается никогда (по 54-ФЗ чек выдаётся при расчёте); в логе — «пропущен».
- Что в чеке: сумма к оплате (как в ссылке ВТБ), название «Тур: <отель>, <город>, <дата вылета>, <ночи>, заказ N» или «Проживание: <отель>, <номер>, <даты>, заказ N», тестовый поставщик (настоящие ИНН / наименование / телефон туроператора — вопрос Ф3), почта — `FERMA_TEST_EMAIL`. Имена, почта и телефон покупателя в чек и в `fiscal_receipts` не попадают.
- `InvoiceId` = `tc-test-<номер заказа>-pay-1`; повтор того же заказа возвращает тот же чек.
- Лог: `[FERMA] booking order=… source=lt receipt=#… invoice=… state=confirmed url=…`.
- Посмотреть: `GET /api/admin/fiscal/receipts?orderRef=<номер заказа>` или `?scenario=booking_lt` — поле `request` — тело, ушедшее в Ferma.
- Выключить: `FERMA_RECEIPT_TRIGGER=off` (по умолчанию) и `pm2 restart api`.

Следующий шаг — `FERMA_RECEIPT_TRIGGER=payment`: чек после подтверждения оплаты ВТБ вместо бронирования.

## 8. Переключение с тестового стенда на боевую кассу (test → live)

Боевые доступы OFD.ru уже в `.env`. Порядок — сначала проверка, потом переключение.

**1. Проверка боевой кассы — чеков не создаёт.**

```bash
cd <папка totus_API> && git pull
node scripts/ferma-live-check.js
```

Скрипт берёт `FERMA_LOGIN`, `FERMA_PASSWORD`, `FERMA_INN` из `.env` и только в своём процессе ходит на `ferma.ofd.ru`. Работающий API и `.env` не меняются. Запросы — только чтение:

- токен — подходят ли боевой логин и пароль;
- кассы — «Готова к работе», ФФД 1.2, признак агента, «только интернет», ИНН 9729424935, место расчётов totus.club, тариф и ФН;
- очередь чеков.

Пароль и токен не печатаются. Последняя строка — `МОЖНО ПЕРЕКЛЮЧАТЬ` (код выхода 0) или `НЕЛЬЗЯ ПЕРЕКЛЮЧАТЬ` с пунктами `FAIL` (код 1, 2 — ошибка настроек).

**2. Переключение** — только после `МОЖНО ПЕРЕКЛЮЧАТЬ`:

```bash
# .env
FERMA_MODE=live
FERMA_INN=9729424935
# FERMA_BASE_URL — удалить (или https://ferma.ofd.ru)
# FERMA_RECEIPT_TRIGGER=off  — в live чек при бронировании не пробивается в любом случае
# FERMA_ALLOW_LIVE_RECEIPTS=0 — тестовые чеки на боевой кассе запрещены
pm2 restart api
pm2 logs api --lines 50 --nostream | grep FERMA   # [FERMA] mode=live host=ferma.ofd.ru inn=9729424935 …
```

**Что меняется после переключения:**

- `/api/admin/fiscal/config`, `/token`, `/cashboxes`, `/queue` показывают боевую кассу;
- фоновая сверка работает только с чеками режима `live` (тестовые строки в `fiscal_receipts` не трогает);
- самопроверка (`selftest`) недоступна;
- тестовые чеки из `POST /receipts` запрещены (`403 live_receipts_disabled`).

**Что не меняется:** чеки при оплате ВТБ по-прежнему не пробиваются — это отдельный PR (раздел 6). Покупатели ничего не замечают.

**Откат:** `FERMA_MODE=test` (и тестовые доступы стенда) или `off`, затем `pm2 restart api`.

**Первый боевой чек** — сценарий Т15 из `FERMA_TESTING_RU.md`: 1 ₽ с возвратом, по отдельному решению владельца.
