# Документы заказа: доступ и хранение

По пункту К1 из `SECURITY_AUDIT_2026-09_RU.md`.

## Что было не так

Ваучеры, авиабилеты, страховки и визы лежали в `uploads/orders/<order_id>/` и
раздавались `express.static` без какой-либо проверки. Имена файлов
предсказуемы (берутся из заголовка документа Level.Travel), `order_id` —
последовательные номера LT. То есть паспортные данные чужих туристов
скачивались перебором. Кроме того, семь каталогов с реальными документами
оказались закоммичены в репозиторий.

## Как стало

| Файл | Роль |
| --- | --- |
| `lib/orderDocLinks.js` | разбор пути и подпись HMAC-SHA256 на `JWT_SECRET` |
| `middleware/signOrderDocLinks.js` | дописывает `?t=…` ко всем ссылкам на документы в исходящем JSON |
| `middleware/orderDocumentsAccess.js` | отдаёт файл только по подписанной ссылке или по Bearer владельца |

Клиентам (сайт, приложение, десктоп) менять ничего не нужно: они получают
ссылку из ответа API уже с токеном и открывают её как раньше. В базе `public_url`
остаётся чистым — подпись живёт только в теле ответа.

Переменные окружения (обе необязательные):

- `ORDER_DOC_LINK_TTL_SECONDS` — срок жизни ссылки, по умолчанию 86400 (сутки),
  допустимый диапазон — от 60 секунд до 7 суток.
- `ORDER_DOCS_ACCESS=log` — аварийный откат: всё отдаётся как раньше, отказы только
  пишутся в лог `[ORDER-DOCS]`. По умолчанию — `strict`.

Попутно закрыт К4: в `utils/levelTravelWebhooks.js` убран fallback-литерал
`PARTNER_API_KEY`, сравнение ключа стало timing-safe, длины ключей больше не
пишутся в лог. **Без `PARTNER_API_KEY` в `.env` webhook'и LT будут отклоняться
с 503** — перед деплоем убедитесь, что переменная задана.

```bash
cd /путь/к/totus_API

# 1. Правки в app.js, utils/levelTravelWebhooks.js и utils/orderEmails.js.

# 3. Убрать чужие документы из репозитория (файлы на диске сервера остаются)
```

Новых зависимостей нет, миграций базы не требуется.

## История git

Удаление из ветки не убирает файлы из истории — документы останутся доступны
любому, у кого есть доступ к репозиторию. После мержа нужна отдельная
чистка (выполняется один раз, переписывает историю, требует force-push и
согласования со всеми, кто работает с репозиторием):

```bash
pip install git-filter-repo
git clone --mirror git@github.com:tosmedia/totus_API.git totus_API-mirror
cd totus_API-mirror
git filter-repo --path uploads/orders --invert-paths
git push --force --all && git push --force --tags
```

После этого всем разработчикам нужно заново клонировать репозиторий.

## Проверка после деплоя

```bash
# 1. Анонимный запрос — должен быть 401
curl -i "https://api.totus.club/uploads/orders/331445018/agreement_doc.pdf"

# 2. Картинки CMS по-прежнему открыты — должен быть 200
curl -I "https://api.totus.club/uploads/banners/<любой-файл>.jpg"

# 3. Ссылка из ответа API открывается: в JSON заказа у ссылок есть ?t=…
curl -s -H "Authorization: Bearer <токен>" \
  "https://api.totus.club/orders/documents?order_id=<свой заказ>" | head -c 400
```

В интерфейсе: открыть свой заказ на сайте и в приложении и скачать ваучер —
должен открываться как раньше.

## Что осталось за рамками этого изменения

- Старые письма, уже разосланные клиентам, содержат ссылки без подписи — они
  перестанут открываться. Документы в тех же письмах идут вложением, так что
  файлы у клиентов остаются.
- Файлы, которые уже лежат в гит-истории, стоит считать скомпрометированными
  до чистки истории.
- Ключ `PARTNER_API_KEY` был в открытом виде в репозитории — его нужно
  перевыпустить у Level.Travel и положить новое значение в `.env`.
