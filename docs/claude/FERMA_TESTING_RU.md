## 0. Коротко

- **Тестовый доступ уже есть и бесплатен.** OFD.ru держит публичный стенд `https://ferma-test.ofd.ru` с общей тестовой организацией, касса ФФД 1.2 с признаком агента и «только интернет» — как нужно нам. Логины опубликованы в документации (§5.2). Договор, КЭП и деньги для этого не нужны.
- **Ограничения стенда:** организация общая (чужие чеки видны в реестре), наш ИНН там не проверить, callback на наш сервер — только после того, как на api.totus.club появится маршрут.
- **Проверено 20.10:** авторизация, наш агентский чек тура, только позиционные агентские данные, повтор `InvoiceId`, статус по `ReceiptId` и `InvoiceId`, частичный возврат, коррекция, ошибки, реестр `list2`, очередь, параметры кассы. 6 расхождений с документацией (§2).
- **Postman:** готовая коллекция из 20 запросов с автоматическими проверками и два окружения — TEST (заполнено) и PROD (пустое, для ТОТУСКЛАБ).
- **Три уровня проверки:** (1) Postman на стенде — сейчас, без кода; (2) наш сервер в режиме `FERMA_MODE=test` на стенде — после backend; (3) боевая касса ТОТУСКЛАБ: Postman по окружению PROD + заказ за 1 ₽ с возвратом.

## 2. Расхождения с документацией (учесть в коде)

| # | В документации | На деле (стенд, 20.10) | Что делаем |
|---|---|---|---|
| Р1 | `AuthToken` — 32 шестнадцатеричных символа | UUID с дефисами (36 символов) | Не проверять формат токена |
| Р2 | Повтор с тем же `InvoiceId` «безопасен, чек не создаётся» | Так и есть, но ответ — **ошибка** 400 / 1019 с `Data.ExistingReceiptId` | Код 1019 считать успехом, брать `ExistingReceiptId` |
| Р3 | Для ФФД 1.2 `PaymentAgentInfo` только в позициях / и в чеке (противоречие) | Работают оба варианта | Передаём только в позиции (по таблице 3.3); подтвердить у поддержки для боевой кассы |
| Р4 | — | Длинное тире «–» в `Label` касса выбрасывает («20.11 27.11»), «ёлочки» превращает в прямые кавычки | В `Label` и названиях — только дефис и прямые кавычки |
| Р5 | Ошибка 1065: одна ставка НДС на чек | Чек с двумя ставками пробит | Всё равно одна ставка на чек (страховка) |
| Р6 | `cashboxes/extended` — 17 полей | Есть ещё `inn`, `kpp`, `taxModeMask`, `agentModeMask`, `isAgent`, `isInternet`, `ffdVersion`, `paymentPlace`, `settlementAddress` и др. | Автопроверка параметров регистрации боевой кассы (§5, Т2) |

**Маски.** У кассы стенда `taxModeMask` = `110111`, и `Unified` отклоняется с 1010 → маска читается справа налево: бит 0 — общая, 1 — УСН доход, 2 — УСН доход − расход, 3 — ЕНВД (0), 4 — ЕСХН, 5 — патент. Это вывод по одному наблюдению; `agentModeMask` (`01111111`) так же не расшифрован в документации — уточнить у поддержки.

## 4. Postman: как запустить

1. Postman → **Import** → три файла: коллекция и два окружения.
2. Справа вверху выбрать окружение **«Ferma TEST (ferma-test.ofd.ru)»**.
3. Запустить папки по порядку — по одному запросу (Send) или всю коллекцию через **Run collection**. Токен получается сам: скрипт коллекции берёт новый, если до конца жизни меньше 5 минут.
4. Результат каждого запроса — вкладка **Test Results** (зелёные / красные проверки) и **Console** (номер ФД, ссылка на чек, статус).
5. Ссылку на чек из консоли открыть в браузере — видно, как чек увидит покупатель.
6. Статусы (2.2, 2.6, 2.8, 2.10, 3.3): если пришёл 0 или 1 — нажать Send ещё раз через пару секунд.

| Папка | Запросы | Что проверяют |
|---|---|---|
| 0. Авторизация | 0.1 | Токен и срок жизни |
| 1. Касса | 1.1, 1.2 | Касса «Готова к работе», ФФД 1.2, агент, интернет; маски систем налогообложения и агентов; тариф и ФН; очередь |
| 2. Чеки | 2.1–2.10 | А (тур), повтор `InvoiceId` → 1019, Д (частичный возврат), Г (Arlekino), Е (коррекция); статусы по `ReceiptId` и `InvoiceId` |
| 3. Ошибки | 3.1–3.5 | Неверный ИНН поставщика → 1085; неверная сумма → `KKT_ERROR`; система налогообложения не из регистрации → 1010; неверный токен → 401 |
| 4. Реестры | 4.1, 4.2 | `list2` и `receipts/extended` за сегодня; фильтр своих чеков по префиксу |

Переменные окружения, которые меняют чаще всего: `amountTour`, `amountReturn`, `amountArlekino`, `vat`, `agentType`, `supplier*`, `arlekino*`, `buyerEmail`, `callbackUrl`. Пароли в окружении PROD — тип `secret`; файл окружения с заполненным паролем не пересылать и не класть в Git.

**Проверка коллекции 20.10:** тела всех 20 запросов после подстановки переменных — валидный JSON, скрипты без синтаксических ошибок; тело запроса 2.1 в точности как его соберёт Postman отправлено на стенд → `CONFIRMED` (ФД 146747). Весь прогон коллекции в самом Postman — за владельцем (из облака Postman не запустить).

## 6. Как проверить весь процесс от начала до конца

**Этап A — стенд через Postman (можно сегодня, без кода и без договора).**
Владелец импортирует коллекцию → прогоняет папки 0–4 → смотрит чеки по ссылкам и в демо-кабинете. Результат: подтверждён формат наших чеков. Основное уже сделано 20.10 (§1); повтор в Postman — чтобы владелец увидел сам.

**Этап B — наш сервер на стенде (после PR в totus_API).**
1. На сервере `FERMA_MODE=test`, переменные стенда; `pm2 restart api`.
2. Скрипт проверки создаёт **тестовый** заказ (номер вне диапазона настоящих) и помечает его оплаченным тем же кодом, что и ВТБ.
3. Ждём: запись в `fiscal_receipts` → `ReceiptId` → callback (в логе адрес отправителя) → `CONFIRMED` → ссылка на чек у заказа.
4. Т4–Т7, Т9–Т14, Т17 по таблице.
5. Через Postman (4.1) — свои чеки в реестре по префиксу `tc-test-`.
6. Убрать тестовый заказ.
Готово, когда все ● в колонке С зелёные, `npm run check` зелёный.

**Этап C — боевая касса ТОТУСКЛАБ (после подключения, раздел 4 плана интеграции).**
1. Окружение «Ferma PROD» в Postman: логин, пароль, система налогообложения, почта владельца.
2. Только 0.1, 1.1, 1.2: касса «Готова к работе», `inn` 9729424935, `ffdVersion` 1.2, `isAgent`, `isInternet`, `paymentPlace`. Если что-то не так — **до первого чека** перерегистрация.
3. На сервере `FERMA_MODE=live`, боевые переменные.
4. Т15: номер Arlekino за 1 ₽ → оплата → чек на почте → «Возврат выполнен» в админке → чек возврата.
5. Проверить оба чека в ЛКК OFD.ru и в «Заказах»; запрос 4.1 в окружении PROD — оба на месте.
6. Через сутки — первая ежедневная сверка и мониторинг (Т14, Т16).

**Критерии «интеграция работает»:**
- каждая оплата → ровно один чек прихода в статусе 2, ссылка на чек у заказа и в письме покупателю;
- каждый выполненный возврат → чек возврата;
- `KKT_ERROR` и ошибки валидации видны в админке, оплата и заказ от них не страдают;
- callback приходит, но статус берётся из `status`; потерянный callback подбирает фоновая сверка;
- ежедневная сверка «оплаты ↔ чеки» без расхождений неделю подряд;
- в логах нет токена и персональных данных.
