## 1. Почему нужен медиасервер

Сейчас звонок идёт напрямую между устройствами (WebRTC P2P, звук шифруется на концах). calling_api_v2 передаёт только offer/answer/ICE. TURN (`turn1.totus.club` = 109.205.58.195, `turn2.totus.club` = 217.60.61.112 — отдельные серверы) пересылает уже зашифрованные пакеты.

Значит, на сервере звонок записать нельзя. Нужен участник посередине: Janus с плагином AudioBridge.

## 2. Архитектура

- На каждый звонок — комната AudioBridge на двоих. Janus сводит звук и пишет запись.
- calling_api_v2 подставляет Janus вместо собеседника:
  - offer звонящего уходит в Janus; answer Janus придерживаем до ответа собеседника;
  - принимающему offer генерирует Janus, его answer уходит в Janus.
- Цель — текущие сборки приложений, сайт, панель и десктоп без изменений. Это **гипотеза**, проверяется прототипом (этап 2).
- API Janus только на 127.0.0.1, с ним работает только calling_api_v2 (библиотека janode). Наружу открыт только UDP под звук.
- Включение — флагом в calling_api_v2: `off → QA-аккаунт → сотрудники → все`. Откат — флаг `off`, звонки снова напрямую.

```
POST /api/calls → calls (ringing) + комната Janus → push / socket как сейчас
Ответ → оба в Janus, запись с момента ответа
Отбой / таймаут → комната закрыта → обработка (janus-pp-rec + ffmpeg) → файл → call_recordings (ready)
Админка → «Звонки»: список, фильтры, карточка, плеер, журнал прослушиваний
```

**Данные (calling_api_v2):**
- `calls` — участники, платформы, время звонка / ответа / конца, итог, причина;
- `call_recordings` — файл, формат, длительность, размер, статус, дата автоудаления;
- `recording_access_log` — кто, когда, с какого IP слушал или скачивал.

**Прослушивание:** ссылка живёт несколько минут, только staff, Range-запросы через internal-location nginx, каждое прослушивание в журнале. Сначала макет, код — после утверждения.

**Закон и правила проекта:**
- голос — персональные данные: предупреждение клиенту, политика (место «запись звонков», D12), уведомление сотрудников;
- записи только на нашем сервере в РФ;
- в Милу / DeepSeek записи не попадают.

## 3. Mute во время записи (разбор 28.10)

- **Запись не останавливается.** Mute = `track.enabled = false`, устройство шлёт пакеты тишины. AudioBridge сводит по своим часам каждые 20 мс, поэтому в смешанной записи на месте молчащего — тишина. Таймлайн непрерывен, после Unmute голос на своём месте.
- **Правило:** Mute реализуется только через `track.enabled`. `replaceTrack(null)` и `removeTrack` не использовать.
- **Стерео из отдельных дорожек:** при сборке выравниваем по меткам времени и заполняем пропуски тишиной. Если каналы расходятся больше 0,5 с, стерео помечается «не собрано» и играет моно. Основной файл — смешанный моно; стерео — дополнительный, после проверки на прототипе.
- **Android, «включил, а меня не слышат»** (`claude/ANDROID_MUTE_ANALYSIS_RU.md`, П2): в записи будет тишина. Это честное отражение разговора, чинится отдельно.
- **Отметки в плеере:** рекомендован вариант «б» — кто когда говорил, по событиям `talking` в Janus, позже. Точные отметки Mute требуют правок во всех клиентах — не рекомендуется.

## 4. Ресурсы (оценка 28.10, подтвердить нагрузочным тестом на этапе 1)

- **Процессор:** звонок — 2–5 % одного ядра (Opus 48 кГц); одно ядро тянет около 20 звонков.
- **Память:** Janus 100–200 МБ + 5–10 МБ на звонок.
- **Сеть:** ~0,1 Мбит/с в каждую сторону на звонок.
- **Диск во время звонка:** ~6 МБ/мин временных файлов.
- **Сжатые записи:** моно 0,24 МБ/мин, моно + стерео 0,72 МБ/мин. 50 звонков в день по 5 мин за 12 мес. — ~22 / ~66 ГБ.
- **Главный риск — соседи по серверу.** Сборка сайта и общие ядра хостинга дают «бульканье» в звуке и в записи.
