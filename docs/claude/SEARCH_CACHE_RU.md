## Зачем

Первый поиск у Level.Travel идёт долго: операторы отвечают по очереди. Замер на проде 26.10.2026 (Москва → Турция, 23.11, 9 ночей, 3 взрослых):

| | Первый поиск | Повторный с теми же параметрами |
|---|---|---|
| Первый готовый оператор | 2,4 с | сразу, все 6 — `cached` |
| Все операторы | 24 с | — |
| Первая страница выдачи (50 отелей, 170 КБ) | 0,6 с | 0,14 с |

Сайт и приложение показывают выдачу, как только готов хотя бы один оператор. При первом поиске человек ждёт 2–5 с и видит выдачу не всех операторов. Повторный поиск быстрый и полный, но кеш Level.Travel живёт около 13 минут от первого поиска, и повторные запросы его не продлевают (замер 26.10: тот же поиск в 13:25 — `cached`, в 13:26 — снова `pending`). Поэтому прогрев самого LT раз в сутки ничего не даст — снимок хранит наш сервер.

## Как работает

1. **Ночной прогрев.** Каждый день в `SEARCH_CACHE_TIME` (по умолчанию 00:05 МСК) сервер сам ищет то, что видит каждый, кто нажал «Найти» без изменений (каждый час его дополняет запланированный чекап, см. выше):
   - все страны из `/references/destinations` (57 на 26.10);
   - Москва, вылет через 7 дней, 7 ночей, 2 взрослых, тур с перелётом.

   По каждой стране сервер ждёт ответа всех операторов (до 90 с) и сохраняет снимок:
   - ответ `enqueue`;
   - итоговые статусы операторов;
   - первую страницу выдачи в том виде, в каком её просят сайт (50 отелей, 3–5★) и приложение (20 отелей, 3–5★).

   Одновременно идут 3 поиска, вся ночь — несколько минут.
2. **Повторный поиск.** Если человек ищет то же самое (сайт или приложение), `/start-search` сразу отвечает из снимка: статусы всех операторов уже итоговые. `/search-status` отдаёт `completeness: 100`, первая страница `/grouped-hotels` — тоже из снимка. Выдача приходит без ожидания и от всех операторов. В ответе есть `cached_at` — время снимка.
3. **Обновление в фоне.** При попадании сервер повторяет этот поиск в Level.Travel в фоне, не чаще раза в `SEARCH_CACHE_REFRESH_MINUTES` (10 мин) на направление, и обновляет снимок. Поэтому:
   - популярные направления днём остаются свежими;
   - кеш Level.Travel тоже прогрет — вторая страница, сортировка и фильтры (они идут в LT, как раньше) отвечают быстро.

   Нагрузка на LT при этом не растёт: без кеша каждый такой поиск сам уходил в LT.
4. **Всё остальное — как раньше.** Другие даты и города, дети, гибкие даты, поиск отеля, только отель, фильтры на первой странице, страница отеля, бронирование идут напрямую в Level.Travel.

Цена в выдаче из снимка может быть старше на часы. Точную цену показывают страница отеля (там свой свежий поиск) и бронирование (актуализация LT). Страну, где LT ничего не нашёл, из снимка не отдаём — там поиск идёт вживую. Снимок старше `SEARCH_CACHE_MAX_AGE_HOURS` (26 ч) не отдаётся.

Снимки хранятся в памяти и на диске (`var/search-cache/`, в Git не попадает) и переживают `pm2 restart`. Если после запуска нет снимков на сегодняшнюю дату вылета, прогрев начинается через минуту. Личных данных в снимках нет — только параметры поиска и выдача отелей.

## Включение

В `.env` API:

```
SEARCH_CACHE=on
```

Затем `git pull && npm run check && pm2 restart api`. В логе:
- `[SEARCH-CACHE] включён: … прогрев каждый день в 00:05 МСК`;
- через минуту — строки по странам;
- в конце — `[SEARCH-CACHE] прогрев после запуска готов: стран 57, с отелями …`.

Остальные переменные (все необязательные) — в `.env.example`: время, город, дни до вылета, ночи, взрослые, список стран, число одновременных поисков, срок снимка, частота фонового обновления, папка.

Выключить — `SEARCH_CACHE=off` и `pm2 restart api`: всё работает как до этого PR.

## Проверка

- `GET /api/admin/search-cache` (токен сотрудника) — прогретые страны, дата вылета, число отелей, возраст снимка, итог последнего прогрева.
- `POST /api/admin/search-cache/warmup` — прогреть сейчас (в фоне).
- На сайте: Москва → Египет с датами по умолчанию → «Найти». Выдача без ожидания. В ответе `/start-search` есть `cached_at`. В логе API — `[SEARCH-CACHE] hit start EG …`.
- `pm2 logs api --lines 500 --nostream | grep SEARCH-CACHE`.
