## 0. Коротко

- **Ferma** — облачная онлайн-касса OFD.ru: касса (Эфир Pro ФС) с фискальным накопителем стоит в дата-центре OFD.ru, мы шлём ей JSON по HTTPS, она пробивает чек и передаёт его в налоговую. OFD.ru одновременно и поставщик кассы, и оператор фискальных данных — отдельный договор с другим ОФД не нужен.
- **Что нужно нам:** после каждой оплаты через ВТБ (СБП, «Мир») автоматически пробивать чек ООО «ТОТУСКЛАБ» и отправлять его покупателю; при возврате — чек возврата. Это уже обещано в документе «Оплата и возврат денег» (п. 3) на сайте.
- **API простое:** 1 метод авторизации + 1 метод создания чека + 1 метод статуса; остальное — отчёты и мониторинг.
- **Главные сложности не в API, а вокруг него:**
  1. **Агентский чек.** ТОТУСКЛАБ — субагент Level.Travel. Чтобы вся сумма тура не стала выручкой ТОТУСКЛАБ, в чеке нужны признак агента и **ИНН, наименование и телефон туроператора** (не Level.Travel) — по каждому заказу. Откуда брать эти данные — открытый вопрос.
  2. **Сервис асинхронный, callback не гарантирован:** без подписи, без повторов. Источник истины — опрос статуса. Нужна фоновая сверка.
  3. **Регистрация кассы в ФНС** с КЭП директора, и параметры регистрации (система налогообложения, признак агента, «только интернет») потом меняются только перерегистрацией.
  4. **Решения бухгалтера:** система налогообложения и НДС ТОТУСКЛАБ в 2026 году, ставка НДС туроператора в агентском чеке, тип договора с Level.Travel.
- **Порядок:** вопросы (раздел 9) → подключение в личном кабинете OFD.ru и регистрация кассы → проверка на тестовом стенде → backend в totus_API → раздел «Чеки» в админке → ссылка на чек в «Заказах» (сначала макет) → боевой запуск на заказе за 1 ₽ с возвратом.

## 1. Как работает Ferma

### 1.1. Схема

```
Покупатель → оплата ВТБ (СБП / «Мир») → /vtb/callback или /check_pay (totus_API)
   → заказ оплачен → totus_API: POST /api/kkt/cloud/receipt (Ferma)
   → Ferma ставит чек в очередь → облачная касса → фискальный накопитель
   → OFD.ru → ФНС;  покупателю — чек на e-mail (или SMS) от OFD.ru
   → Ferma: POST на наш CallbackUrl (CONFIRMED / KKT_ERROR)  +  мы опрашиваем /status
   → у нас: номер ФН, номер документа, фискальный признак, ссылка на чек (OfdReceiptUrl)
```

### 1.2. Ключевые свойства

| Свойство | Что в документации | Что значит для нас |
|---|---|---|
| Форматы | Кассы работают с ФФД 1.1 и 1.2 (1.05 не поддерживается с 11.2023) | Регистрируем кассу на ФФД 1.2 |
| Транспорт | HTTPS, JSON UTF-8, заголовок `Content-Type: application/json` обязателен | — |
| Асинхронность | Получение `ReceiptId` — не конец пробития. Финал — через callback или методы `status` / `list` / `list2`. Если callback не пришёл за 300 с — опросить статус | Заказ получает статус чека «в процессе», финал — позже |
| Дубли | Повтор запроса с тем же `InvoiceId` новый чек не создаёт | Безопасные повторы при тайм-ауте сети. Стенд 20.10: ответ на повтор — HTTP 400, код 1019 и `Data.ExistingReceiptId`; считать это успехом |
| Перепробитие | После ошибки кассы (`StatusCode: 3`) отправлять с **новым** `InvoiceId` | Нужна схема нумерации попыток |
| Балансировка | Ferma сама распределяет чеки по кассам клиента | Можно взять 2 кассы для отказоустойчивости |
| Лимит | Около 2000 запросов на каждую активную кассу за 60 минут (динамически) | Для нашего объёма достаточно одной кассы |
| Ручные чеки | В личном кабинете есть «Пробить новый чек» | Запасной путь, если API недоступен |

## 2. API — справочник

### 2.1. Хосты и авторизация

| | Боевой | Тестовый |
|---|---|---|
| Хост | `https://ferma.ofd.ru` | `https://ferma-test.ofd.ru` |
| Логин / пароль | из личного кабинета OFD.ru (раздел Ferma) после покупки услуги | публичные, в документации §5.2 (для ФФД 1.1 и 1.2 — разные) |
| Демо-кабинет для просмотра чеков | — | `https://lk-demo.ofd.ru` (данные входа — документация §5.3) |

Пароли тестового стенда в этот документ не копирую: файл зеркалится в Git.

**Получение токена:** `POST /api/Authorization/CreateAuthToken`, тело `{"Login": "...", "Password": "..."}` → `Data.AuthToken` (по документации 32 шестнадцатеричных символа; на стенде 20.10 — UUID с дефисами, формат не проверять) и `Data.ExpirationDateUtc` (UTC+0, формат `ГГГГ-ММ-ДДTчч:мм:сс`).

**Все остальные запросы:** токен передаётся **в строке запроса** `?AuthToken=...`. Документация сама предупреждает: он попадает в access-логи, историю, аналитику. У нас — маскировать в своих логах (axios, `[FERMA]`), не логировать полный URL.

### 2.2. Общий формат ответа

- Успех: HTTP 200, `{"Status": "Success", "Data": {...}}` (при разбиении большого чека — `DataList`).
- Ошибка: HTTP ≠ 200, `{"Status": "Failed", "Error": {"Code": <≠0>, "Message": "..."}}`; ошибки валидации — ещё `Data.ValidationErrors[]` с `FieldName` и `Description`.

### 2.3. Методы

| Метод | Запрос | Зачем нам |
|---|---|---|
| Создание чека | `POST /api/kkt/cloud/receipt?AuthToken=` | **Основной.** Приход, возврат, коррекция |
| Статус чека | `POST /api/kkt/cloud/status?AuthToken=`, тело `{"Request":{"ReceiptId":"..."}}` или `{"Request":{"InvoiceId":"..."}}` | **Источник истины** о результате |
| Реестр чеков | `POST /api/kkt/cloud/list` (серверное время) и `/list2` (время кассы), тело с `StartDateLocal` / `EndDateLocal` (обязательны), `ReceiptId`, `StartDateUtc`, `EndDateUtc` | Ежедневная сверка «оплаты ↔ чеки» |
| Реестр с деталями | `GET /api/kkt/cloud/stats/receipts/extended?AuthToken=&dateFromIncl=&dateToIncl=&receiptId=&zn=&fn=` (даты по Москве, `YYYY-MM-DD hh24:mi:ss`) | Отчёт для бухгалтера |
| Список ФН за период | `GET /api/kkt/cloud/stats/fn/aggregates?dateFrom=&dateTo=&AuthToken=` | Справочно |
| Мониторинг касс и ФН | `GET /api/kkt/cloud/stats/cashboxes/extended?AuthToken=&deviceId=&rnm=&zn=&fn=` | Предупреждения: статус кассы, конец тарифа, заполнение и срок ФН |
| Очередь | `GET /api/kkt/cloud/stats/receipts/queue/length?AuthToken=` | Мониторинг задержек |
| Проверка маркировки (ТС ПИоТ) | `POST /api/kkt/cloud/mc/piot/check/getdata` | **Не нужно** — у нас нет маркированных товаров |

### 2.4. Запрос на чек — поля, которые важны для Totus Club

Структура: `{"Request": {Inn, Type, InvoiceId, CallbackUrl, CustomerReceipt: {...}, Cashier: {...}}}`.

| `InvoiceId` | наш идентификатор попытки, см. §5.4 |
| `CallbackUrl` | `https://api.totus.club/api/ferma/callback/<секрет>` — проверяется регуляркой, `?`, `&`, `=` допустимы |

### 2.5. Статусы чека и что с ними делать

| `StatusCode` | `StatusName` | Финальный? | Действие |
|---|---|---|---|
| 0 | `NEW` — принят Ferma | нет | Опрашивать. Висит больше 24 часов — проверить кассы и тариф, затем в поддержку OFD.ru |
| 1 | `PROCESSED` — сформирован на кассе | нет (устаревший промежуточный) | Опрашивать до финала |
| 2 | `CONFIRMED` — передан в ОФД | да | Сохранить `Device`: `RNM`, `ZN`, `FN`, `FDN`, `FPD`, `ShiftNumber`, `ReceiptNumInShift`, `OfdReceiptUrl` |
| 3 | `KKT_ERROR` — ошибка на кассе | да | Причина в `StatusMessage` / `Description` (например «[-3975] Некорректное значение параметров команды ФН»). Исправить данные и отправить с **новым** `InvoiceId` |
| — | ответ 1004 «Объект не найден» на `status` | — | Запрос до Ferma не дошёл — отправить чек заново |

### 2.6. Callback

- Приходит POST на `CallbackUrl` только по финальным статусам 2 и 3. Тело — как ответ `status` плюс `ReceiptId` и `InvoiceId`.
- **Подписи нет.** Любой 2xx — принято. На 4xx, 5xx и тайм-аут (10 с) — запись в журнал Ferma и **удаление из очереди, без повторов**. Скорость отправки — до 30 в секунду.
- Отправляется с адресов `94.143.160.0/24`, `94.143.161.0/24`, `185.15.172.16/29` — разрешить их на сервере.
- Документация прямо советует считать основным источником метод `status`, а дубли отсекать по `ReceiptId` / `InvoiceId`.

**Вывод для нас:** callback — только сигнал «проверь». Получив его, отвечаем 200 сразу и сами запрашиваем `status` по `ReceiptId`; данные из тела callback как истину не берём (его может прислать кто угодно, знающий адрес). Плюс фоновая сверка (§5.6).

## 3. Как это ложится на Totus Club

Исходные данные проекта:
- деньги туриста принимает ООО «ТОТУСКЛАБ» на счёт в ВТБ (СБП по QR, карты «Мир»); касса и чек — ТОТУСКЛАБ;
- ТОТУСКЛАБ — турагент и субагент Level.Travel; туроператор — тот, что указан в заказе;
- оплата сейчас подтверждается в `POST /vtb/callback` (`processVtbCallback`) и `POST /check_pay`; после оплаты уходит уведомление `paid` в Level.Travel;
- номера Arlekino (`order_id ≥ 900000000`) оплачиваются тем же путём, но без Level.Travel; продавец размещения в этом контуре — ООО «АРЛЕКИНОТУР»;
- возвраты Arlekino — вручную; возвраты по турам приходят от Level.Travel в `POST /tours/level_travel/order_refund`.

### 3.1. Агентский чек — главное правило

- По разъяснениям ФНС, когда посредник принимает деньги за чужую услугу, в чек добавляются: признак агента (тег 1057 на весь чек или 1222 на позицию), **ИНН поставщика (1226)** и данные поставщика — наименование (1225) и телефон (1171). Без них **вся сумма считается выручкой агента**.
- Указывается **поставщик услуги, а не ближайший агент**: для тура — туроператор, а не Level.Travel.
- В Ferma для `AgentType` = `AGENT`, `COMMISSIONER`, `CONFIDANT` обязательны только `SupplierInn`, `SupplierName`, `SupplierPhone` (таблица 3.7); поля банковских и платёжных агентов не заполняются.
- `AgentType` выбирается по типу договора с Level.Travel: агентский → `AGENT`, комиссии → `COMMISSIONER`, поручения → `CONFIDANT` (бухгалтер, вопрос Ф2).
- **Противоречие в документации Ferma для ФФД 1.2:** в таблице 3.3 сказано, что `PaymentAgentInfo` передаётся только в позициях и не может быть на уровне чека; а в сноске 13 — что если он есть в позиции, то и на уровне чека должен быть `PaymentAgentInfo` с `AgentType`. Пример в §3.2.4 передаёт оба. **Стенд 20.10 (касса ФФД 1.2): работают оба варианта** — берём только позиционный, как в таблице 3.3; для боевой кассы подтвердить у поддержки.
- Кассу при регистрации нужно отметить как применяемую агентом (с нужным типом агента) — иначе ошибка 1029.
- Сумму своего вознаграждения в чеке туристу выделять не требуется.

### 3.2. Сценарии и какие чеки пробивать

| # | Сценарий | Чек ТОТУСКЛАБ | Поля Ferma | Кто пробивает следующий чек |
|---|---|---|---|---|
| А | Тур Level.Travel, оплачен полностью | Приход, «предоплата 100 %», агентский | `Type: Income`, `PaymentMethod: 1`, `PaymentType: 4`, `AgentType` по договору, поставщик — туроператор | Чек «полный расчёт» при оказании услуги, как правило, пробивает туроператор (исполнитель). ## 5. Что сделать с нашей стороны (технический трек, без кода)

### 5.1. Где живёт интеграция

**totus_API** — там подтверждение оплаты ВТБ, заказы и вебхуки Level.Travel. Отдельный сервис не нужен.

| Часть | Назначение |
|---|---|
| `lib/ferma/client` | Токен (кэш до `ExpirationDateUtc` минус 5 минут, обновление при 401 / 1001), запросы с тайм-аутом, маскирование `AuthToken` в логах, повтор при сетевой ошибке с тем же `InvoiceId` |
| `lib/fiscal/build` | Чистые функции: заказ + платёж → тело чека (сценарии А–Е). Деньги в копейках, проверки §2.4 до отправки |
| `lib/fiscal/service` | Создать запись → отправить → обновить статус; идемпотентность |
| Таблица `fiscal_receipts` | §5.2 |
| `POST /api/ferma/callback/:secret` | Сигнал «проверь статус» (§2.6) |
| Фоновая сверка | §5.6 |
| `/api/admin/fiscal/*` | Для раздела «Чеки» в админке (только staff) |
| Справочник поставщиков | Если ИНН / наименование / телефон туроператора не приходят из Level.Travel — таблица `operator_id → ИНН, наименование, телефон` в админке |

### 5.2. Таблица `fiscal_receipts` (черновик)

`id`, `order_id`, `payment_ref` (id операции ВТБ), `kind` (`income` / `return` / `correction`), `invoice_id` (уникальный), `attempt`, `receipt_id`, `amount_kop`, `status_code` (0–3), `status_message`, `rnm`, `fn`, `fdn`, `fpd`, `ofd_receipt_url`, `receipt_date`, `request_hash` (без персональных данных), `error_code`, `error_text`, `created_at`, `updated_at`. E-mail покупателя здесь не хранится — он в заказе.

### 5.3. Где запускается пробитие

| Событие | Код сейчас | Что добавить |
|---|---|---|
| Оплата подтверждена | `processVtbCallback` (`/vtb/callback`) и `/check_pay` — оба пути помечают заказ оплаченным | Один вызов «создать чек прихода» **после** фиксации оплаты; оба пути сходятся в нём, повтор не создаёт второй чек (уникальность `order_id + payment_ref + kind`) |
| Возврат по туру | `/tours/level_travel/order_refund` | Чек возврата на сумму фактического возврата **в момент выплаты денег** покупателю, а не по уведомлению (выплату делаем мы) — привязать к действию «возврат выполнен» |
| Возврат Arlekino | вручную в админке | Кнопка «Возврат выполнен» → чек возврата |
| Коррекция | — | Кнопка в админке с обязательным описанием причины |

Оплата никогда не ждёт кассу: если Ferma недоступна, чек ставится в очередь повторов, заказ и уведомление Level.Travel идут как сейчас.

### 5.4. `InvoiceId`

Формат `tc-<order_id>-<kind>-<attempt>`, например `tc-123456789-pay-1`, `tc-123456789-ret-1`. Повтор после тайм-аута — тот же `InvoiceId`; после `KKT_ERROR` — `attempt + 1`. На тестовом стенде — префикс `tc-test-`, чтобы не пересечься с боевыми номерами.

### 5.5. Режимы и настройки

`FERMA_MODE=off|test|live` (по умолчанию `off` — поведение API не меняется), `FERMA_BASE_URL`, `FERMA_LOGIN`, `FERMA_PASSWORD`, `FERMA_INN`, `FERMA_CALLBACK_SECRET`, `FERMA_TAXATION_SYSTEM`, `FERMA_AGENT_TYPE`, `FERMA_BILL_ADDRESS`. Секреты — только в `.env` сервера.

### 5.6. Фоновая сверка и мониторинг

- Каждые 1–2 минуты: чеки в статусах 0 / 1 старше 5 минут → `status`; оплаченные заказы без чека → создать чек.
- `KKT_ERROR`: ошибки данных — в админку с уведомлением владельцу; ошибки кассы (1070–1079, «нет свободных касс») — автоматический повтор с паузой.
- Раз в сутки: `list2` за прошлые сутки против оплат ВТБ — расхождения в отчёт.
- Раз в сутки: `cashboxes/extended` — `kktState` не «Готова к работе», `tariffEndDate` меньше чем через 14 дней, `fnVolumePercent` и `projectedFnReplaceDate` — предупреждение владельцу.
- Логи с префиксом `[FERMA]`: номер заказа, `InvoiceId`, статус, время ответа; без e-mail, телефона и токена.

### 5.7. Пользователю

- Чек приходит на почту от OFD.ru автоматически.
- В «Заказах» (сайт, приложения, десктоп) — строка «Кассовый чек» со ссылкой `OfdReceiptUrl`, как обещано в документе «Оплата и возврат денег». Это видимое изменение интерфейса — **сначала макет и «утверждаю»** (оркестратор §3.7), затем PR в totus_WEB, totus_APP, totus_desktop. API отдаёт ссылку в заказе (в т. ч. в лёгком списке `?view=list`).

### 5.8. Админка (Totus_admin)

Раздел «Чеки»: список с фильтрами (статус, дата, заказ), карточка (запрос без персональных данных, ответ, ссылка на чек), «Повторить», «Чек возврата», «Чек коррекции», справочник поставщиков. Только сотрудники (staff). Тоже через макет.

### 5.9. Юридические документы

- Политика обработки персональных данных: OFD.ru — получатель e-mail / телефона покупателя для отправки чека (в документах уже есть пустое поле «ОФД» — заполнить: ООО «ПЕТЕР-СЕРВИС Спецтехнологии», бренд OFD.ru; реквизиты сверить по договору).
- «Оплата и возврат денег», п. 3 — уже соответствует; после запуска проверить, что чек действительно есть в «Заказах».

### 5.10. Проверки (по регламенту, шаг 4)

`scripts/check-ferma-*.js` в `npm run check` на чистом Node с подменой HTTP: сборка чеков А–Е (суммы, НДС, длина `Label`, агентские поля), идемпотентность (двойной callback ВТБ → один чек), статусы 0→2 и 3→повтор с новым `InvoiceId`, обновление токена, маскирование токена в логах, callback с чужими данными не меняет статус без запроса `status`.

## 7. Риски и сложности

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Нет данных туроператора (ИНН, наименование, телефон) в заказе Level.Travel | Нельзя пробить агентский чек → вся сумма в выручке ТОТУСКЛАБ | Вопрос Ф3 в Level.Travel; запасной вариант — справочник поставщиков в админке, чек не уходит, пока поставщик не заполнен (с уведомлением) |
| Неверный тип агента или система налогообложения при регистрации | Ошибка 1029 / отказ в чеках; исправление — только перерегистрация | Решить Ф1, Ф2 **до** подписания заявки |
| Противоречие в документации по `PaymentAgentInfo` (ФФД 1.2) | Чеки отклоняются или теги не те | Стенд + поддержка OFD.ru |
| Callback без подписи и без повторов | Чек «завис» или подделанный статус | Callback только как сигнал; статус и сверка — сами |
| Токен в строке запроса | Утечка через логи | Маскирование; полный URL не логируем |
| Ferma или касса недоступны в момент оплаты | Чек не в момент расчёта | Очередь повторов; если не удалось — чек коррекции |
| Ставка НДС в агентском чеке | Неверные данные в ФНС | Бухгалтер (Ф4); ставка на заказ одна (ошибка 1065) |
| Изменения НДС 2026 (22 %, НДС для упрощёнки сверх порога) | Неверная ставка или система налогообложения | Бухгалтер (Ф1) |
| Арлекинотур в чеке | Противоречит решению 05.10 | Решение владельца (Ф6) |
| Частичные возвраты (минус фактические расходы) | Сумма чека возврата не совпадает с исходным | Чек возврата на фактически выплаченную сумму в момент выплаты |
| Округление | Ошибки 1015 / 1085 | Деньги в копейках; `Price × Quantity = Amount` проверяется до отправки |
| E-mail покупателя неверный | Чек уйдёт на почту организации | Валидация; при неверном — телефон, если есть |
| Конец тарифа, срок или заполнение ФН | Касса перестаёт пробивать, риск снятия с учёта | Ежедневный мониторинг `cashboxes/extended` |
| Оплаты, принятые до запуска кассы | Нарушение 54-ФЗ за прошлые расчёты | Если такие есть — чеки коррекции (Ф12) |
