### Support App: соединение сразу после «Ответить» без открытия приложения (дополнение к задаче ниже)
- **Уточнение владельца.** Приложение закрыто, в фоне или телефон заблокирован. После «Ответить» в CallKit звонок должен соединиться сам: открывать приложение вручную не нужно. Первая версия исправления соединяла звонок только после открытия, поэтому основной сценарий она не решала.
- **Причина** (подтверждена кодом `AppDelegate.swift` после коммита «fix ios 27»). React Native запускался только в `SceneDelegate.scene(willConnectTo:)`. Когда VoIP-пуш будит закрытое приложение, iOS не подключает сцену, пока пользователь не откроет приложение. Поэтому JS не работал: CallKit звонил (это делает нативная часть), но соединять звонок было некому.
- **Дополнительно найдено:**
  - На iOS `didActivateAudioSession` от CallKit игнорировался. На экране блокировки аудиосессию включает CallKit, а WebRTC об этом не сообщалось — риск звонка без звука.
  - Сокет после долгого фона уходил с просроченным access-токеном (12 ч).
- **Сделано:**
  - `ios/TotusSupport/AppDelegate.swift`: в обработчике VoIP-пуша, после отчёта в CallKit, вызывается `startReactNativeInBackgroundIfNeeded()`. Он запускает React Native без окна через `factory.rootViewFactory.view(withModuleName:)` (API RN 0.79.7 сверено с исходниками). При открытии приложения сцена показывает тот же root view, второй экземпляр JS не создаётся.
  - `src/voip/coldStart.ts` + `index.js`: движок звонков поднимается из сохранённой сессии сразу при старте JS, до монтирования UI (только iOS).
  - `VoipService.ts`: на iOS `didActivateAudioSession` / `didDeactivateAudioSession` → `RTCAudioSession.audioSessionDidActivate/Deactivate` (react-native-webrtc 124). Активация, случившаяся до старта JS, восстанавливается из отложенных событий CallKeep.
  - `src/api/voipAuth.ts`: перед подключением сокета просроченный токен обновляется.

### Support App: ответ на VoIP-звонок из фона / закрытого приложения не соединяется — ветка `claude/support-voip-background-answer` (PR ещё не создан: ждёт «добро»)
- **Симптом.** Приложение закрыто, в фоне или неактивно. Приходит VoIP-пуш, сотрудник отвечает, приложение открывается, но соединение не устанавливается.
- **Причины** (найдены по коду, воспроизведены проверкой на исходном `main` @ `15d4510b`):
  1. **iOS, закрытое приложение.** Ответ в CallKit происходит до того, как JS зарегистрировал обработчики. RNCallKeep держит его в очереди отложенных событий, забрать которую можно только через `getInitialEvents()`. Код читал очередь только на Android, поэтому на iOS ответ терялся. Проверка на исходном коде: 0 соединений.
  2. **Повторная обработка одного ответа.** `processPendingAnswer` вызывался из 5 мест: таймер инициализации, каждое событие VoIP-токена (до 5 запросов токена), ветка повторной инициализации, очередь из фона. `pendingAnswerCallUUID` не сбрасывался. Каждый вызов создавал новый `RTCPeerConnection` и затирал предыдущий. Проверка на исходном коде: 5 соединений на один звонок.
  3. **Поздний пуш сбрасывал состояние.** После выхода из фона событие пуша могло прийти после ответа и вернуть состояние «ringing».
  4. **Нет устройства и сети после долгого фона.** На iOS при холодном старте ответ уходил без `deviceId`, так как токен приходит позже. Оффер запрашивался всего 4 с (8×500 мс).
  5. **Нет очистки при сбое** `processPendingAnswer`: экран оставался в «answered». Остатки прошлого звонка (блокировка, UUID) могли блокировать новый.
- **Сделано** (один слой — клиент `totus_support_app`):
  - Новый модуль `src/voip/answerRecovery.ts` (чистая логика): свёртка отложенных событий CallKeep по порядку («ответ, потом сброс» — не соединять); «один ответ на звонок»; паузы запроса оффера (10 попыток, около 25 с); решение при возврате в приложение.
  - В `src/voip/VoipService.ts`:
    - `recoverCallKeepInitialEvents` — на iOS и Android, при инициализации и при каждом возврате в приложение;
    - `schedulePendingAnswer` — единственный вход для отложенного ответа, идемпотентный;
    - `handleAnswerCall` и `processPendingAnswer` защищены от повторов;
    - ожидание `deviceId` до ~6 с перед ответом;
    - обработчик AppState `active` для обеих платформ: переподключение сокета, завершение ответа или перезапуск ICE;
    - очистка и завершение звонка при сбое, сброс устаревшей блокировки;
    - поздний пуш не сбрасывает принятый звонок и сохраняет оффер из пуша.
- **Проверено.** Добавлен `scripts/check-voip-answer-recovery.mjs` (`npm run check`, Node ≥ 22.18, без `npm install`). Настоящий `VoipService.ts` запускается с подменёнными нативными модулями: 13 проверок. На исправленном коде 13/13. На исходном 5 падают: 0 соединений на iOS, 5 соединений вместо 1, сброс в «ringing», ответ без `deviceId`. Typecheck на заглушках — новых ошибок нет (набор ошибок заглушек совпадает с исходным).
- **Не проверено:** реальное устройство или TestFlight — сборки в облаке нет. Нативная часть: при запуске от PushKit в фоне JS стартует только при открытии приложения (SceneDelegate), поэтому соединение устанавливается после открытия — как и требуется.

### Регистрация в приложении «Signup failed» — [totus_API #26](https://github.com/tosmedia/totus_API/pull/26) (слит)
- **Симптом:** ошибка при регистрации из приложения. Исправить нужно без обновления приложения.
- **Причина (по коду, логами не подтверждена).** Приложение шлёт только имя и email, без `l_name` и `phone`. При NOT NULL-колонках INSERT падает в `catch` → 500 «Signup failed». Второй возможный источник — сбой отправки письма.
- **Сделано** (`controllers/auth.controller.js`):
  - пустые `l_name` / `phone` подставляются по nullability колонок из INFORMATION_SCHEMA;
  - при сбое письма пользователь удаляется, ответ 502 с понятным текстом;
  - лог `[SIGNUP]`.
- **Проверено:** на поддельной БД — запрос как из приложения → 201; повтор email → 400; запрос как с сайта → 201; сбой письма → 502 и повтор → 201; без имени → 400.
- **Осталось:** деплой + проверка из приложения (D4), закоммитить проверку (D2).
