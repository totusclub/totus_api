# TOTUS — регламент работы чатов (WORKFLOW)

**Введён владельцем 29.09.2026.** Цель — не терять контекст между чатами и при пересоздании облачного контейнера.

Этот регламент **добавляется** к действующим правилам и их не меняет:
- `docs/CLAUDE_ORCHESTRATOR_RU.md` §3 — зоны чатов, ветки `claude/*`, «добро» перед коммитом, доска Totus Dev Board, «сначала макет — потом код», секреты, язык;
- архитектурные решения в `claude/ROADMAP_RU.md` §3 (в том числе: персональные данные не передаются в ИИ).

При противоречии действуют правила оркестратора.

---

## 0. Три файла состояния — обновлять после ЛЮБОГО изменения

| Файл | Что в нём | Когда обновлять |
|---|---|---|
| `claude/STATUS_RU.md` | Текущее состояние: что открыто, слито, развёрнуто, что сломано, долги, кто что сейчас делает | В начале задачи — строка в «Сейчас в работе»; в конце — итог |
| `claude/JOURNAL_RU.md` | Журнал по датам (новые записи сверху): что сделано, почему, чем проверено, ссылки на PR | После каждого изменения |
| `claude/WORKFLOW_RU.md` | Этот регламент | Только по решению владельца |

«Любое изменение» — это PR, коммит, правка Figma, новый документ, решение владельца, выявленная поломка.

Записывать в таком порядке:
1. **JOURNAL** — новая запись.
2. **STATUS** — актуальные таблицы.
3. **Тематический документ** задачи (`claude/<ТЕМА>_RU.md`), если он есть.

Все файлы живут в проекте Claude «Totus Dev» (`project_write`) — это общая память всех чатов. Правило «всегда после любого изменения обновлять STATUS, JOURNAL, WORKFLOW» — требование владельца.

**Копия в Git (решение владельца 01.10.2026: «Храни всё это в `totus_API/docs` и всегда поддерживай MD-файлы в актуальном состоянии»).** Каждый документ проекта зеркалится в репозиторий `tosmedia/totus_API`:
- проект `claude/<x>` → репо `docs/claude/<x>`; проект `docs/<x>` → репо `docs/<x>`;
- после каждой записи в проект тот же файл пушится через коннектор **только в ветку `claude/docs-sync`** (решение владельца 02.10.2026: «Ветка `claude/docs-sync` — всегда обновляй только здесь») и сверяется по blob SHA;
- в `main` и в ветки задач документы не кладём; PR из `claude/docs-sync` не открываем — слияние, если нужно, делает владелец;
- перед push — проверка на секреты (значения ключей, паролей, токенов не коммитить);
- проект остаётся основным источником для чатов; при расхождении верным считается проект, Git догоняется.

## 1. Порядок работы над каждой задачей

### Шаг 1. Прочитать состояние
- Открыть `claude/STATUS_RU.md`, верхние записи `claude/JOURNAL_RU.md` и тематический документ задачи.
- Сверить с GitHub: не слиты ли или не закрыты ли PR из STATUS с момента последней записи. Для этого использовать `search_pull_requests` / `list_pull_requests`.
- Если облачный контейнер пересоздался, нужные файлы заново скачиваются из GitHub через коннектор:
  - репозиторий нельзя клонировать токеном сессии;
  - большие ответы коннектор сохраняет в файл, их извлекать оттуда;
  - blob SHA каждого файла сверять `git hash-object`.
- Добавить строку в STATUS → «Сейчас в работе»: чат, задача, репозиторий/слой, время. Это нужно, чтобы параллельные чаты не правили одно и то же.

### Шаг 2. Причина, а не симптом
- На «не работает» — лезть в код и по возможности воспроизводить. Способы:
  - живые запросы только на чтение через коннектор Groover (`http_fetch` к api.totus.club, apiv2.totus.club, totus.club);
  - headless Chromium для вёрстки;
  - поддельная БД / fetch / LLM для серверной логики.
- Заказы, оплаты и персональные данные в проверках не трогать.
- Догадку без проверки называть догадкой: «не подтверждено, потому что…».

### Шаг 3. Правка — один слой
- Один репозиторий на один PR, ветка `claude/<тема>` от `main` (или от ветки, указанной в STATUS).
- **calling_api_v2:** основная рабочая ветка продакшена — `prod` (подтверждено владельцем 30.09). Ветка `claude/<тема>` создаётся от `prod`, PR открывается в `prod`.
- Если слой уже занят другим чатом по «Сейчас в работе» — не трогать, написать владельцу.
- Видимые изменения UI — только после макета и «утверждаю» (оркестратор §3.7).

### Шаг 4. Тесты на то, что чинили
- Каждая проверка — из реальной поломки, не «для галочки».
- Проверки коммитятся в репозиторий в тот же PR, а не остаются во временной папке:
  - `scripts/check-*.js` (`*.ts`);
  - totus_API: подключить в `npm run check` (на 29.09 — 13 скриптов + `node --check app.js`).
- В репозиториях без набора проверок (totus_ai_v2, totus_WEB, Totus_admin и др.) набор заводится с первой же задачи: `scripts/check-*.{js,ts}` + скрипт `check` в `package.json`.
- Перед PR прогонять **весь** набор репозитория, не только новый тест. Количество проверок записывать в STATUS → «Проверки».
- Ограничение среды: npm-реестр из облака закрыт (403), поэтому полноценных `npm install` / build / lint нет. Проверки должны работать на чистом Node (подмена модулей через `require.cache`, глобальные `tsc` / `tsx`, заглушки типов). Что проверить не удалось — писать в PR и в JOURNAL.

### Шаг 5. Записать
JOURNAL → STATUS → тематический документ, всё в проект Claude и копией в `totus_API/docs` (см. §0).

### Шаг 6. Перенести в GitHub со сверкой
- Push только через коннектор GitHub (`push_files` / `create_or_update_file`) в ветку `claude/*`. Токен сессии `GITHUB_TOKEN` для push не использовать. Мак для переноса не нужен.
- После каждого push — сверка: blob SHA каждого изменённого файла в ветке (`get_file_contents`) должен совпасть с `git hash-object` локальной проверенной копии. Расхождение устранить до открытия PR.
- Особые символы при передаче через коннектор:
  - неразрывный пробел, U+2011, U+FE0F передавать `\u`-экранированием;
  - в новых комментариях не использовать псевдографику (─), её легко исказить.
  - опыт 01.10: `\uXXXX` в содержимом файла коннектор превращает в сам символ (и в `push_files`, и в `create_or_update_file`). Для строк JS использовать `\u{XXXX}` — тот же символ, коннектор его не трогает.
- Файлы больше ~60 КБ и файлы с секретами коннектор может не пропустить — такие файлы владелец пушит сам.
- PR создаётся с описанием: проблема → причина → что сделано → как проверено → что сделать владельцу. Сливает и деплоит только владелец.
- Перед коммитом — явное «добро» владельца (оркестратор §3.5).

### Шаг 7. Коротко отчитаться
Что было сломано → почему → что теперь → 2–3 действия, которые остались за владельцем, со ссылками на PR.

## 2. Как отмечать развёртывание

- «Слит» проверяется в GitHub.
- «Развёрнут» — со слов владельца или по живому маркеру (например, новое поле в ответе API, новый CSS-класс на сайте). В STATUS указывать, чем подтверждено.
- Если маркера нет — писать «не подтверждено».
